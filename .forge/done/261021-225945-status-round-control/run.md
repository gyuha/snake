## 계획과 실제의 차이
1. **먹이 초기화를 하지 않았다.** 계획의 "점수와 먹이를 초기화"에서 먹이는 뺐다. 서버가 섹터별 먹이를 이벤트(추가·먹힘)로만 클라이언트에 알려서, 먹이를 조용히 비우면 재참가하는 클라이언트와 상태가 어긋날 수 있다. 모든 뱀을 죽이면 사망 먹이가 새로 깔리고 자연 먹이는 기존 목표량이 유지되므로 공정성에는 큰 영향이 없다고 봤다. 점수는 뱀이 새로 만들어지므로 0에서 시작한다.
2. 라운드 종료·시작 알림은 새 메시지 `round`를 모든 세션(플레이어 포함)에 보낸다. 접속 직후, 상태 변화 시, 진행 중 1초마다 전송한다.
3. 서버에 `now` 옵션을 추가했다(테스트에서 시계를 움직여 1분을 기다리지 않기 위함). 계획에는 없던 테스트용 주입점이다.
4. 시작 요청은 관전 세션(`spectate`를 보낸 소켓)만 보낼 수 있게 했다. 계획의 "관전 소켓이 보낸다"를 서버에서 강제한 것이다. 공개 URL이라는 점은 그대로이며 접근 제한은 여전히 없다.
5. 수동 검증용 서버는 8080이 이미 다른 프로세스(이전 코드)로 점유되어 있어 8181/5191로 띄웠고 검증 후 내 프로세스만 종료했다. 8080의 기존 서버는 건드리지 않았다. **그 서버는 새 코드가 아니므로 재시작해야 새 기능이 보인다.**

## 실행 후 추가 요청: 종료 시 내 순위 표시
실행 완료 후 사용자가 "게임이 종료되면 내 순위를 표시"를 요청했다. 이미 실행된 계획은 고치지 않는 규칙이라 계획은 그대로 두고 이 `run.md`에 소규모 후속 변경으로 기록한다.
- 결정: 순위는 플레이어 화면(index.html) 종료 오버레이에 표시한다. 종료 시점에 살아 있으면 `내 순위 N / M · 점수`, 이미 죽었으면 `탈락 · 최종 점수 X점`, 한 번도 참가하지 않았으면 표시 없음. 서버·프로토콜 변경 없음(기존 leaderboard의 `myRank`와 death의 `finalScore` 사용).
- 구현: `formatMyResult`(round-clock.ts, 단위 테스트 4개 선 실패 확인 → 통과), `#my-result` 요소, main.ts에서 종료 상태일 때 갱신. 순위는 서버가 1초마다 보내는 값이라 종료 직후 최대 1초 전 값일 수 있다.
- 검증: `npm test` 198개 통과, typecheck 통과, 브라우저에서 1분 라운드 종료 후 "내 순위 29 / 31 · 30점" 확인(`/tmp/player-ended-rank.png`). 탈락 문구는 단위 테스트로만 확인했다.
- status.html(관전 화면)에는 "나"가 없어 변경하지 않았다.

## 실행 후 추가 요청 2: 시작 시 팝업 없이 점수만 초기화 + "게임 시작" 배너
- 요청: 시작 버튼을 눌러도 팝업(플레이어의 사망 화면)을 보이지 말고 점수만 초기화한다. 대신 "게임 시작"을 큰 글씨로 빠른 페이드 인·아웃, 1.5초간 보여 준다.
- **앞선 결정을 뒤집는다**: "시작 시 플레이어 뱀을 모두 사망 처리"(그릴링 결정 9)를 폐기했다. 이제 모든 뱀(봇 포함)을 사망 이벤트·사망 먹이 없이 조용히 치우고, 플레이어는 같은 닉네임·스킨·동물로 새로 스폰한다(새 `welcome`로 `selfId` 갱신). 봇은 다음 틱에 다시 채워진다. 그래서 `World.killAll`은 `clearSnakes`로 대체했다(내가 만든 것이라 미사용으로 남기지 않음).
- 해석 가정: "점수만 초기화"를 "길이·점수가 처음 상태로 돌아가는 새 뱀"으로 해석했다(위치도 새로 정해진다). 뱀을 그 자리에 두고 길이만 줄이는 방식은 클라이언트 동기화가 복잡해 택하지 않았다. 새 뱀의 시작 점수는 0이 아니라 처음 길이의 점수다.
- 프로토콜: `round` 메시지에 시작 번호 `seq`(u8, 시작할 때마다 +1)를 추가했다. 클라이언트가 재시작과 반복 방송을 구분해 배너를 한 번만 띄우기 위함이다. 첫 메시지(접속 직후)에는 배너를 띄우지 않는다.
- 배너는 status.html뿐 아니라 플레이어 화면에도 띄운다(요청은 status.html 맥락이었지만, 사망 팝업이 사라지는 대신 시작을 알리는 신호가 필요하다고 보았다). 필요 없으면 index.html과 main.ts에서 빼면 된다.
- 검증: `npm test` 201개 통과, typecheck 통과. 서버 테스트(사망 메시지 없음·새 welcome·같은 이름/스킨/동물·시작 번호 증가), `RoundClock` 단위 테스트, 브라우저로 status 화면 배너(`/tmp/status-banner.png`)와 플레이어 화면(사망 팝업 없음, `/tmp/player-after-start.png`) 확인. 플레이어 탭이 백그라운드여서 배너가 남아 보였다(브라우저가 숨은 탭의 CSS 애니메이션을 멈춤). 1.5초 타이밍과 페이드 모양은 눈으로 재지 않았고 CSS 키프레임 값으로만 지정했다.

## 실행 후 추가 요청 3: 시작 버튼 옆에서 봇 수 설정(0~100)
- 요청: status.html 시작 버튼 옆에 봇 개수 입력, 최대 0~100.
- 해석 가정(확인받지 않음): 봇 수는 시작 버튼을 누를 때 함께 적용된다(입력만으로 바로 바뀌지 않음). 기본값은 기존 봇 수 30. 서버는 마지막으로 시작할 때 받은 값을 유지한다. 시작이 월드를 비우고 다시 채우므로 줄이는 쪽에 별도 제거 로직이 필요 없다.
- 구현: `startRound`에 `bots`(u8) 추가, 서버가 0~100 밖이면 무시(`BOT_MAX`), `ServerOptions.onStartRound`로 호스트에 전달, `BotController.setTarget`, index.ts에서 연결. 입력란 `#bots`(0~100, 기본 30)를 분 입력과 시작 버튼 사이에 두고 범위 밖이면 시작 버튼 비활성화. 좁은 화면에서 컨트롤 줄이 넘치지 않도록 `flex-wrap`을 켰다.
- 검증: `npm test` 205개 통과(프로토콜 왕복, 서버의 0·100 허용과 101·255 무시, `setTarget` 테스트를 먼저 실패시킨 뒤 통과), typecheck 통과. 봇 100마리 서버 6초 구동: 평균 틱 1.59ms·최대 11.2ms(30마리는 0.52ms·1.3ms)로 33ms 예산 안. 브라우저에서 봇 7 입력 후 시작 → 순위표 7명 확인(`/tmp/status-bots7.png`).
- 확인하지 못한 것: 봇 100을 UI로 실제 입력해 보지는 않았다(서버 수치와 테스트로 갈음). 좁은 화면의 줄바꿈 모양은 눈으로 보지 않았다. 봇 0일 때 UI 동작은 서버 단위 테스트(`setTarget(0)`)로만 확인했다.

## 실행 후 추가 요청 4: status.html 왼쪽 하단에 게임 접속 QR코드
- 요청: 게임 접속 주소를 QR코드로 왼쪽 하단에 표시.
- 결정(확인받지 않음): QR이 가리키는 주소는 `status.html`을 연 주소의 origin(`location.origin + '/'`, 게임 페이지)이다. 그래서 **status.html을 `localhost`로 열면 QR도 localhost를 가리켜 휴대폰에서는 안 열린다.** 휴대폰으로 접속시키려면 PC에서 status.html을 LAN 주소(예: `http://192.168.0.74:5173/status.html`)로 열어야 한다. QR 아래에 실제 주소를 글자로 함께 보여 준다.
- 의존성 추가: `qrcode-generator@2.0.4`(MIT, 의존성 없음)를 `@snake/client`에 추가했다(QR 인코더를 직접 짜지 않기 위해). `npm audit`의 경고는 기존 vitest/vite 계열이며 이번 추가와 무관하다.
- 구현: `ui/qr.ts`(`qrModules` 순수 함수 + `drawQr`), status.html의 `#qr-box`(흰 배경·여백으로 quiet zone 확보), status.ts에서 그린다. 서버·프로토콜 변경 없음.
- 검증: `npm test` 209개 통과(finder 패턴·크기·결정성 테스트와 HTML 요소 검사를 먼저 실패시킨 뒤 통과), typecheck 통과, `vite build` 성공. 브라우저에서 왼쪽 하단 표시 확인(`/tmp/status-qr.png`)과 Chrome `BarcodeDetector`로 캔버스를 판독해 `http://localhost:5191/`가 나오는 것까지 확인.
- 확인하지 못한 것: 실제 휴대폰 카메라로 스캔하지는 않았다(브라우저 판독기로 갈음). 좁은 화면에서 QR 박스가 맵과 겹치는 모양은 보지 않았다.

## 실행 후 추가 요청 5: QR을 localhost가 아닌 IP 주소로
- 요청: QR(과 주소 글자)에 localhost 대신 IP를 쓴다. 요청 4의 "localhost로 열면 휴대폰에서 안 열림" 문제를 해결한다.
- 구현: 브라우저는 자기 LAN IP를 알 수 없어 서버가 알려 준다. 새 서버 메시지 `serverInfo{hosts: string[]}`(S2C 0x36)를 `spectate`를 보낸 세션에만 한 번 보낸다. 서버는 `os.networkInterfaces()`의 비내부 IPv4 목록을 쓴다(`ServerOptions.lanHosts`로 테스트에서 주입). 클라이언트의 `gameUrl`(순수 함수)은 호스트가 `localhost`/`127.0.0.1`/`[::1]`일 때만 첫 LAN 주소로 바꾸고 스킴과 포트는 유지한다. 이미 IP나 도메인으로 열었으면 그대로 쓴다. 서버 정보가 오기 전과 LAN 주소가 없을 때는 기존처럼 열린 주소를 쓴다. HTTP 엔드포인트는 CORS로 LAN 주소가 노출되므로 택하지 않았다.
- 알려진 한계(확인받지 않음): 이 개발 머신에는 `en7 192.168.0.74`와 `en0 192.168.0.81` 두 인터페이스가 있고 첫 번째(.74)를 쓴다. 둘 다 같은 192.168.0.x 대역이라 같은 공유기의 휴대폰이면 어느 쪽이든 열릴 것으로 보지만, 휴대폰에서 실제로 열어 보지는 않았다. 인터페이스가 다른 대역(VPN, 가상 어댑터 등)이면 첫 번째가 휴대폰에서 안 닿는 주소일 수 있다. 8080(서버)과 5173(Vite) 방화벽 허용은 별도 사안이다.
- 검증: `npm test` 213개 통과(프로토콜 왕복, 서버가 관전자에게만 `serverInfo`를 보냄, `gameUrl` 단위 테스트를 먼저 실패시킨 뒤 통과), typecheck 통과. 브라우저에서 `http://localhost:5191/status.html`을 열었을 때 QR 판독값과 주소 글자가 `http://192.168.0.74:5191/`로 바뀌는 것 확인(`/tmp/status-qr-ip.png`). 주소 글자가 `519 / 1/`로 줄바꿈되는 것을 보고 한 줄(nowrap)로 고쳤다(`/tmp/qr-box.png`).
