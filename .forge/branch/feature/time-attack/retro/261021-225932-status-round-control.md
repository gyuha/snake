# 2026-10-21 — status.html에서 시간제한 라운드 시작·종료 컨트롤

## 계획 대비 실제
- 계획대로 된 것: 4개 조각 모두 TDD로 완료했다(프로토콜 `startRound`·`round`, 서버 라운드 상태와 종료 정지, status.html 컨트롤·카운트다운·종료 오버레이, 플레이어 HUD). 테스트는 179개에서 213개가 되었고 모두 통과, typecheck 통과, 진행 중·종료 화면은 확정 시안과 같게 나왔다.
- 차이점:
  - 실행 뒤 후속 요청 5건이 이어졌다: 종료 시 내 순위, 팝업 없는 점수 초기화와 "게임 시작" 배너, 봇 수 설정(0~100), QR코드, QR의 IP 표시. 모두 `run.md`의 "실행 후 추가 요청" 절에 남겼다.
  - 그중 하나가 그릴링 결정 9("시작 시 플레이어 뱀 사망 처리")를 뒤집었다. 그릴링에서는 status.html 시안만 보여 주었고, 시작 순간 플레이어 화면에 사망 화면이 뜬다는 사실은 구현 뒤에야 드러났다.
  - 먹이 초기화는 계획에서 뺐다. 서버가 먹이를 이벤트로만 알려서 조용히 비우면 클라이언트 상태가 어긋난다.
  - 서버에 `now`, `lanHosts` 같은 테스트용 주입점이 계획 없이 생겼다.
  - 브라우저 확인 이벤트가 자동 알림으로만 전달될 때는 사용자 답으로 보지 않고 터미널에서 다시 확인받았다(진행 중 타이머 위치, 종료 화면). 안전하지만 같은 답을 두 번 받는 비용이 들었다.

## 배운 점
- 다음에는 이렇게 한다:
  - 서버가 상태를 바꾸는 기능(리셋, 시작, 종료)은 그릴링 때 모든 클라이언트(플레이어 화면 포함)가 그 순간 어떻게 보이는지 시안이나 질문으로 먼저 확인한다. 이번에는 관전 화면만 시안으로 확정해 플레이어 사망 팝업이라는 결과를 놓쳤다.
  - 브라우저가 알 수 없는 값(LAN IP 등)이 필요한 기능은 처음부터 서버가 알려 주는 구조로 설계한다(`serverInfo`). 브라우저의 `location`만으로는 해결되지 않는다.
  - `run.md`에는 변경이 실제로 적용된 것을 확인한 뒤에 적는다. macOS의 BSD `sed`가 조용히 실패했는데 "적용했다"고 먼저 적은 일이 있었다. 파일 편집은 `sed -i` 대신 편집 도구를 쓰고 `grep -c`로 확인한다.
  - 포트 8080에 이전 코드의 서버가 떠 있으면 다른 포트(8181/5191)로 서버와 vite를 따로 띄워 확인하고, 내가 띄운 프로세스만 끈다. 이전 작업(`animal-head-tail-skins`)에서도 같은 일이 있었다.
  - 라운드처럼 1분 걸리는 흐름은 서버에 시계(`now`)를 주입해 테스트에서 시간을 움직인다. 브라우저 확인은 1분 라운드로 줄여서 실제로 한 번 돈다.
  - 숨은 탭에서는 브라우저가 CSS 애니메이션을 멈춘다. 배너처럼 짧은 애니메이션은 포그라운드 탭에서 확인한다.
- 확인된 것: 서버가 라운드 시작을 번호(`seq`)로 알리면 클라이언트가 재시작과 반복 방송을 구분해 배너를 한 번만 띄울 수 있다. 봇 100마리에서도 평균 틱은 1.59ms로 틱 예산(33ms) 안이다.

## 문서 반영
- CONTEXT.md 승급: 라운드 (Round), 종료 상태 (Ended) — 그릴링 중에 이미 반영됨. 추가 승급 없음.
- ADR 추가: 없음. "라운드 컨트롤을 인증 없이 공개"는 맥락 없이는 의아하고 트레이드오프도 있지만, 나중에 막는 비용이 작아 '되돌리기 어려움' 조건이 약했다(사용자 확인). 이유는 이 회고와 후속 후보에 남긴다.
- 회귀 검사(eval) 승급: 없음. 라운드 상태 전이, 분·봇 수 범위 검증, 사망 없는 리셋, 시작 번호, `serverInfo`가 이미 이 작업에서 영구 테스트로 남았다.
